## OWASP Top 10 이란?

- **OWASP**(Open Worldwide Application Security Project)가 뽑은 "웹에서 가장 중요한 보안 위험 10가지" 목록.
- 쉽게 말하면 **"웹 개발 시 가장 자주·위험하게 뚫리는 10가지 체크리스트"**.
- 이 문서 기준: **2025판**(2026년 1월 확정), 이전은 2021판.

## 2025년 주요 변화

- **신규 2개**: 소프트웨어 공급망 실패(#3), 예외 상황 처리 미흡(#10)
- **SSRF 흡수**: 단독 항목에서 빠지고 #1 접근 제어 실패에 포함
- **순위 이동**: 보안 설정 오류 ↑(#5→#2), 암호화 실패 ↓(#2→#4), 인젝션 ↓(#3→#5)

## Top 10 (2025) 한눈에 보기

| # | 항목 | 쉽게 말하면 | 우리 실습 |
|---|---|---|---|
| 1 | 접근 제어 실패 (Broken Access Control) | 로그인 후 "하면 안 되는 범위"에 접근한 것을 못 막음 (id 바꿔 남의 것) | **2강 IDOR** |
| 2 | 보안 설정 오류 (Security Misconfiguration) | 기본 비번·불필요 기능·오류 노출 등 설정 실수 | **9강 Actuator 노출** |
| 3 | 소프트웨어 공급망 실패 (Supply Chain) | 외부 라이브러리·빌드도구 오염이 내 앱까지 전파 | — |
| 4 | 암호화 실패 (Cryptographic Failures) | 민감정보를 제대로 암호화 안 함 | BCrypt·JWT키 |
| 5 | 인젝션 (Injection) | 입력이 "명령"으로 실행됨 (SQL/명령/XSS) | **1강 SQLi** |
| 6 | 안전하지 않은 설계 (Insecure Design) | 구현이 아니라 "설계 자체"의 결함 | — |
| 7 | 인증 실패 (Authentication Failures) | 신원 확인·인증을 제대로 못해 계정 탈취 | JWT·세션(예정) |
| 8 | 무결성 실패 (Integrity Failures) | 검증 없이 코드·데이터가 바뀜 (역직렬화 등) | JSON(예정) |
| 9 | 로깅·경보 실패 (Logging & Alerting) | 공격을 기록·감지·대응 못함 | — |
| 10 | 예외 상황 처리 미흡 (Exceptional Conditions) | 오류 시 안전하지 않게 무너져 정보 노출/통제 우회 | 오류 숨김(반영) |

## 2021 vs 2025 비교

| 순위 | 2021 | 2025 |
|---|---|---|
| 1 | 접근 제어 실패 | 접근 제어 실패 (유지, SSRF 흡수) |
| 2 | 암호화 실패 | 보안 설정 오류 (↑5→2) |
| 3 | 인젝션 | **소프트웨어 공급망 실패 (신규)** |
| 4 | 안전하지 않은 설계 | 암호화 실패 (↓2→4) |
| 5 | 보안 설정 오류 | 인젝션 (↓3→5) |
| 6 | 취약·오래된 구성요소 | 안전하지 않은 설계 (↓4→6) |
| 7 | 식별 및 인증 실패 | 인증 실패 (이름 변경) |
| 8 | 무결성 실패 | 무결성 실패 (유지) |
| 9 | 보안 로깅·모니터링 실패 | 로깅·경보 실패 (이름 변경) |
| 10 | 서버측 요청 위조(SSRF) | **예외 상황 처리 미흡 (신규)** |

> 2021 "취약·오래된 구성요소" → 2025 "공급망 실패"로 확장. SSRF는 #1에 흡수.

## 보충: #3 공급망 실패와 의존성 관리

`pom.xml`이 선언하는 외부 라이브러리(+전이 의존성)가 곧 "공급망"이다. 하나라도 취약·오염되면 앱이 감염된다.

**Maven 의존성 관리**
- **버전 고정** — 정확한 버전, `SNAPSHOT`·범위 지양 (Spring Boot 부모 BOM 활용, 이 앱도 사용)
- **전이 의존성 파악** — `./mvnw dependency:tree`
- **취약점 스캔** — OWASP Dependency-Check, GitHub Dependabot
- **SBOM 생성** — CycloneDX 플러그인으로 부품표 작성
- **신뢰 저장소** — 체크섬·서명 검증, Maven Central·사내 미러만

```bash
./mvnw dependency:tree                             # 전이 의존성 확인
./mvnw org.owasp:dependency-check-maven:check      # 알려진 CVE 스캔
```

**npm(참고): `package-lock.json`**
- `package.json`=선언, `package-lock.json`=**전체 의존성 트리의 정확한 버전을 잠금**
- 범위 버전만 있으면 설치 시점에 악성 버전이 들어올 수 있음 → **반드시 커밋 + CI에서는 `npm ci`**
- Maven은 별도 lock 파일이 없고, **정확 버전 + BOM**이 그 역할을 한다

> 핵심: **무엇을 쓰는지 정확히 알고(inventory), 취약점을 스캔하고, 검증된 버전만 신뢰하기.**

## 보충: #4 암호화 하드닝 체크리스트

이 앱 기준, 암호화 실패를 줄이기 위한 점검 목록.

- **HTTPS/TLS 강제** — JWT·비밀번호 평문 전송 방지, HSTS 적용 (이 앱의 가장 큰 공백, 현재 HTTP만)
- **secret·자격증명 외부화** — JWT secret·DB 비번을 환경변수/시크릿 매니저로 (소스·`properties`에 두지 않기)
- **강한 해시** — 비밀번호는 BCrypt(현재) 또는 Argon2. cost 상향(10→12)
- **강한 알고리즘** — AES-256, TLS 1.3. 약한 것(MD5·SHA-1·DES·RC4) 금지
- **키 관리** — 충분한 길이(HS256 ≥256bit), 정기 교체
- **안전한 난수** — 토큰·키 생성에 `SecureRandom`

> **이 앱 상태**: BCrypt 해시·HS256·키 길이 검증은 **이미 적용됨**. 남은 숙제는 **HTTPS 적용 + JWT secret·DB 비번 외부화**.
> BCrypt·JWT secret의 상세 동작은 별도 **JWT 보안** 문서에서 다룬다.

## 보충: #6 안전하지 않은 설계와 SDLC

**구현(코딩) 실수가 아니라, 설계·아키텍처 자체에 보안이 빠진 것**이다. 코드를 아무리 잘 짜도 설계가 틀리면 못 막는다.
- 예: 비밀번호 재설정을 "보안 질문"만으로 설계, 이체 한도 미설계, 쿠폰 중복 미방지
- 우리 앱의 **IDOR**도 "리소스별 소유권 검사"를 **설계에 넣지 않아** 생긴 것

**SDLC(Software Development Life Cycle)** = 소프트웨어 개발 생애주기
```
요구사항 → 설계 → 구현 → 테스트 → 배포 → 유지보수
```
- "개발 초기부터 보안" = 요구사항·설계 단계부터 보안을 넣는 것(**Shift Left**)
- 설계에서 잡으면 비용 적음. 배포 후 발견 시 **수십~수백 배**

**설계 단계 보안 고려사항**
- **위협 모델링** — "누가·무엇을·어떻게 공격할까" 미리 분석(STRIDE)
- **인증/인가 설계** — 접근 규칙을 설계에 명시 (우리 IDOR 연결)
- **최소 권한 / 기본 거부**, **안전한 기본값(Secure by Default)**
- **심층 방어 / 안전한 실패(fail closed)**
- **비즈니스 로직 악용 방지** — 한도·속도 제한·중복 방지

> **핵심**: 프로필 조회를 설계할 때 "user가 id를 바꿔 남의 것 보려 하지 않을까?"를 미리 떠올렸다면 IDOR은 애초에 안 생겼다.
> Insecure Design은 다른 모든 항목의 **뿌리**다.

### 위협 모델링 — STRIDE

마이크로소프트의 **위협 분류 체계**. 공격 유형을 6가지로 나눠 빠짐없이 점검하며, 각 위협은 깨뜨리는 보안 속성과 1:1로 연결된다.

| 글자 | 위협 | 위반 속성 | 우리 앱 예시 |
|---|---|---|---|
| **S** | Spoofing (위장) | 인증 | JWT 위조·세션 탈취 |
| **T** | Tampering (변조) | 무결성 | 요청·JWT payload 조작 |
| **R** | Repudiation (부인) | 부인방지 | 로그 부재로 행위 증명 불가 |
| **I** | Information Disclosure (정보 노출) | 기밀성 | **IDOR·SQLi로 유출** |
| **D** | Denial of Service (서비스 거부) | 가용성 | 무한 요청으로 다운 |
| **E** | Elevation of Privilege (권한 상승) | 인가 | 일반 user가 admin 접근 |

**사용법**: 시스템(구성요소·데이터 흐름·신뢰 경계)을 그린 뒤, 각 요소에 6가지를 대입해 위협을 찾고, 위협마다 방어를 정한다.

> 프로필 조회를 STRIDE로 점검했다면 **I(정보 노출=IDOR)·E(권한 상승)**를 설계 단계에서 미리 발견했을 것이다.

## 보충: #9 로깅·경보 방어 상세

핵심은 "제대로 기록 → 이상 감지 → 빠른 대응". 요즘 실패는 "데이터가 없어서"가 아니라 **"있는데 아무도 안 봐서"** 생긴다.

- **① 무엇을 로깅** — 인증(로그인 성공/실패·로그아웃), 인가 실패(403·권한 상승), 중요 데이터 변경(관리 작업), 예외
- **② 로깅하면 안 되는 것** — 비밀번호·JWT·세션ID·카드번호 금지(유출 시 2차 피해). 필요시 마스킹
- **③ 어떻게** — 구조화 로깅(JSON) + 타임스탬프·사용자·IP·상관ID(MDC traceId), SIEM·ELK로 중앙 집중(상관분석)
- **④ 탐지·경보** — 다수 로그인 실패(무차별 대입)·비정상 IP·대량 조회(enumeration) 규칙, 임계치+이상탐지, 담당자 연계
- **⑤ 보관·보호·대응** — 90~180일+ 보관, append-only·접근제어로 무결성(공격자가 로그 삭제 못하게), 경보→SOAR 연계, 정기 훈련

**이 앱(Student_JWT) 실천 항목**
- 로그인 성공/실패 기록 — Spring Security 인증 이벤트 리스너(`AuthenticationSuccess/FailureEvent`)
- 403·예외 로깅 — `@RestControllerAdvice`(DefaultExceptionAdvice)에서 기록
- 민감정보 제외 — JWT·비밀번호를 로그에 남기지 않기(마스킹)
- 감사·구조화 로깅 — Actuator audit events, log4j2 JSON + MDC traceId

> 한 줄 정리: **중요한 것 남기고(민감정보는 빼고) → 한 곳에 모아 → 이상 감지·경보 → 안전하게 보관 → 대응 절차와 연결.**

## 보충: #10 오류 메시지 숨김의 두 층

"오류 메시지 숨김"은 한 설정이 아니라 **두 층**으로 이해해야 한다.

**층 1 — Spring Boot 기본 오류 처리기**
- `@ControllerAdvice`가 잡지 못한 오류(매핑 안 된 500 등)의 기본 응답을 통제. 최신 Spring Boot(2.3+)는 이미 `never`가 기본(명시는 의도 문서화).
```properties
server.error.include-stacktrace=never
server.error.include-message=never
```

**층 2 — `@RestControllerAdvice` (이 앱의 실제 처리)**
- 이 앱은 대부분 예외를 `DefaultExceptionAdvice`로 처리 → 위 설정을 **우회**하고 advice 응답이 나간다.
- ⚠️ **이 앱 이슈**: 500(RuntimeException) 핸들러가 `e.getMessage()`를 그대로 응답 → 내부 오류(SQL·NPE 등) 노출 위험
```java
@ExceptionHandler(RuntimeException.class)   // 500
protected ResponseEntity<ErrorObject> handle(RuntimeException e) {
    errorObject.setMessage(e.getMessage());  // ← 내부 메시지가 클라이언트로
    ...
}
```

> **원칙**: 외부엔 일반 메시지 + 상관ID(traceId), 내부 로그엔 상세 예외·스택트레이스. 
> **참고**: 실제 코드 개선(500 일반화, catch-all 핸들러, traceId)은 별도 하드닝 `feature/exception-hardening`(로깅 브랜치 기반)에서 다룬다.

## 보충: #1 접근 제어 실패 vs #7 인증 실패 (자주 헷갈리는 구분)

둘 다 무단 접근을 부르지만, **신원·권한 생애주기의 다른 단계**에서 발생한다.

| 구분 | **#7 인증 실패** (Authentication) | **#1 접근 제어 실패** (Access Control) |
|---|---|---|
| 질문 | "너 누구야?" (신원 확인) | "이걸 할 권한 있어?" (권한) |
| 실패 예 | 약한 비밀번호, MFA 부재, 세션 탈취 | IDOR, 권한 상승 |
| 단계 | 로그인(신원 확립) | 로그인 후 리소스 접근 |

- **순서**: 먼저 로그인(인증)으로 신원을 확립 → 그 뒤 리소스 접근 시 권한(인가) 확인
- **IDOR(2강)**은 "인증은 통과했지만 인가가 빠진" 경우 → **#1**에 해당

> 한마디로: **인증(Authentication) ≠ 인가(Authorization)**.
